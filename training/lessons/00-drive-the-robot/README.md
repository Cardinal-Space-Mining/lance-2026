# Lesson 0: Drive the Robot

**Time:** ~1 hour (after setup) &nbsp;·&nbsp; **Code written:** none

## What you'll do
You'll launch the simulated LANCE robot, drive it with a controller, and use the `ros2` command line
tools to see how it works inside. By the end you'll have drawn a map of how a joystick press
becomes a moving robot.

## Why it matters
The robot software is made of many small programs (**nodes**) that talk to each other. Before you
write a node, you need to know how to see what's running and what data is flowing. You'll use these
same tools every time you debug the real robot.

## Background
Skim these official tutorials (about 10 minutes each):
- [Understanding nodes](https://docs.ros.org/en/lyrical/ROS-Framework/nodes/Working-with-nodes/Understanding-ROS2-Nodes/Understanding-ROS2-Nodes.html)
- [Understanding topics](https://docs.ros.org/en/lyrical/ROS-Framework/interfaces/topics/Understanding-ROS2-Topics/Understanding-ROS2-Topics.html)
- [Understanding services](https://docs.ros.org/en/lyrical/ROS-Framework/interfaces/services/Working-with-services/Understanding-ROS2-Services/Understanding-ROS2-Services.html)

| Term | Meaning |
|------|---------|
| **Node** | One running program, e.g. `robot_control` or `motor_sim` |
| **Topic** | A named channel nodes publish data to and subscribe to, e.g. `/lance/track_left/info` |
| **Message** | The data type sent on a topic, e.g. `phoenix_ros_driver/msg/TalonInfo` |
| **Service** | A request/response call, e.g. `/lance/set_teleop_mode` turns the robot on |
| **Workspace** | The `lance-ws` folder. `src/` holds code, `build/` and `install/` are generated by `colcon` |
| **Sourcing** | `source install/setup.bash` tells your terminal where the built packages are. **You need to do this in every new terminal.** |

## Step 1: Build and launch the simulation
If you haven't already, follow the [full install guide](../../../doc/full-install-guide.md) through
step 10 ("Run the simulation" and "Connect Foxglove"). The short version:

```bash
cd ~/code/lance-ws
./src/build.sh --l2
./src/run.sh gz_full:=lance2_ksc gz_gui:=enabled
```

Connect Foxglove to `ws://localhost:8765` and import `src/foxglove_layout.json`.

✅ **Checkpoint:** You can see the robot in the Gazebo window and data in Foxglove.

## Step 2: Drive the robot
1. Plug in an Xbox-style controller.
2. In Foxglove, click the green **Enable** button (the "Enable Robot" panel).
3. Drive! Try the tracks (left stick), the trencher (right trigger), the hopper belt (left trigger), and raising
   the hopper (right stick). Hold a bumper to reverse the trencher or belt. **A** stops everything.

> [!NOTE]
> [CONTROLS.md](../../../lance/CONTROLS.md) lists every binding, including the assisted routines. The source of
> truth is the code: [`hid_bindings.hpp`](../../../lance/src/robot/core/hid_bindings.hpp) maps each button and
> axis to what it does. Reading it is good practice. Can you find which button toggles the mining stall check
> without looking at CONTROLS.md?

✅ **Checkpoint:** The robot moves in Gazebo, and the "Motors" plot in Foxglove changes when you move the sticks.

## Step 3: Explore with the `ros2` CLI
Leave the simulation running and open a **second terminal**. Source the workspace first:

```bash
cd ~/code/lance-ws
source install/setup.bash
```

Work through these commands and **write down your answers** to the questions.

| Command | What it shows | Question |
|---------|---------------|----------|
| `ros2 node list` | All running nodes | How many nodes are running? Which one do you think reads the controller? |
| `ros2 topic list` | All topics | Find the topics for the left track motor. What two topics does each motor have? |
| `ros2 topic info /lance/track_left/info` | Who publishes and subscribes | Which node publishes motor info? Which nodes subscribe to it? |
| `ros2 interface show phoenix_ros_driver/msg/TalonInfo` | The fields in a message | What units do you think `velocity` and `supply_current` are in? |
| `ros2 topic echo /lance/track_left/info --field velocity` | Live values of one field | Drive forward. What happens to the number? Drive backward? |
| `ros2 topic hz /lance/track_left/info` | How often messages arrive | How many times per second does the motor sim publish? |
| `ros2 topic echo /joy` | Raw controller input | Press buttons and move sticks. Which index in `axes` is the left stick's up/down? |
| `ros2 topic info -v /lance/track_left/info` | Detailed info, including **QoS** | What is the `Reliability` of the publisher? (You'll need this in Lesson 1.) |
| `ros2 node info /motor_sim` | Everything one node uses | List the topics `motor_sim` subscribes to. |

> [!TIP]
> Press `Ctrl` + `C` to stop `echo` and `hz`. Press `Tab` to autocomplete topic and message names.

## Step 4: Call a service
The Foxglove **Enable** and **Disable** buttons call a service. You can call it yourself:

```bash
ros2 service call /lance/set_teleop_mode std_srvs/srv/SetBool "{data: false}"
```

Try driving. Then enable it again with `data: true`.

✅ **Checkpoint:** You turned the robot off and on from the terminal.

## Step 5: Draw the system map (your deliverable)
On paper or a whiteboard, draw boxes for these nodes and arrows for the topics between them:

- `joy_node` (reads the controller)
- `mission_control` (the "driver station" program, `lance/src/client_node.cpp`. It also provides the Enable service)
- `robot_control` (the main robot program, `lance/src/control_node.cpp`)
- `motor_sim` (pretends to be the motor controllers, `lance/src/motor_sim.cpp`)
- Gazebo (the physics simulator)
- Foxglove bridge

Use `ros2 node info` and `ros2 topic info` to work out the arrows. Label each arrow with the topic name and
message type. Follow the path from **pushing the left stick** to **the robot moving in Gazebo**.

*Hint:* The joystick data doesn't go straight to `robot_control`. Find out who else touches it on the way.

Show your diagram to a mentor. They'll compare it with how the real robot works: on the robot, the
`phoenix_driver` node replaces `motor_sim` and talks to real motor controllers over CAN bus.

## Check your understanding
1. What's the difference between a topic and a service? When would you use each?
2. Why does each motor have both a `/ctrl` and an `/info` topic? Which direction does data flow on each?
3. If you open a new terminal and `ros2 topic list` shows almost nothing, what did you probably forget?
4. `motor_sim` and the real `phoenix_driver` publish the same topics with the same message types.
   Why is that useful?
